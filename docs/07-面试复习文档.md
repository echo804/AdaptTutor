# 07-面试复习文档：AdaptTutor 通用自适应学习引擎

> 用途：面试前通读。以"第一人称项目经历"组织，覆盖选型理由、架构、功能实现、真实难点、临场处理与追问预案。
> 配套资料：`01-技术栈选型对比.md`（选型细节）、`03-项目架构.md`（架构图纸）、`ADR-*.md`（决策记录）。

---

## 0. 一句话定位

**AdaptTutor 是一个领域无关的自适应学习引擎**：学科内容以"领域包"（纯 JSON 配置）接入，引擎提供"诊断 → 路径规划 → 苏格拉底式引导辅导 → 错题溯源 → 遗忘调度复习"的完整学习闭环，不绑定任何学科（已接入初中数学、大学英语、LLM 应用开发）。

**核心差异点（区别于普通聊天机器人）**：
1. 不直接给答案——四态状态机 + 六层防泄题机制
2. 数据不丢、状态唯一——学习闭环以 PG 单一真相源串起来
3. 效果可验证——每个知识点有量化掌握度（BKT 概率 + SM-2 复习调度）
4. 内容可插拔——领域包是纯配置，接新学科零改引擎代码

技术栈：Next.js 14 + TypeScript + React Flow + motion / FastAPI + SQLAlchemy(asyncpg) + PostgreSQL 16 + LiteLLM / Docker Compose（阿里云 2C4G 单机部署）。

## 1. 技术栈选型：每个选择背后的约束

**总决策准则**：单机 16GB 内存约束优先；复杂度换必要性；能砍则砍，接口后置（可替换的模块留 repository/接口层，不提前引入重组件）。

| 选型 | 候选 | 结论与核心理由 |
|---|---|---|
| 后端框架 | FastAPI / Flask / Django | **FastAPI**。对话流式输出需要 WebSocket 原生支持；异步 IO 契合 LLM 调用；Pydantic 同时服务请求校验与领域包 schema 校验。Django 全家桶在单机项目里是负担 |
| 图谱存储 | PG JSONB / Neo4j / pgvector | **PG JSONB + 应用层图算法**。图谱规模是"单章节 30-50 节点"，依赖查询是浅层遍历，PG 内跑完全够；Neo4j 唯一优势（原生图查询）在 ≤500 节点规模上不成立，代价却是 16GB 机器上最贵的 3-5GB 内存 + 独立运维。**弃用 Neo4j** |
| 题目检索 | 标签过滤(SQL) / Qdrant / pgvector | **标签过滤**。领域包 1 题库仅 100+ 题，按"知识点标签+难度+错误模式"组合过滤覆盖全部检索。question_bank 预留 embedding 字段，规模 >5000 再引入 pgvector（同库零新进程） |
| 任务队列 | FastAPI BackgroundTasks / Celery+Redis | **后台任务**。耗时任务只有诊断计算与报告生成（分钟级、无跨进程诉求），状态持久化在 PG，重启可恢复。Celery 的持久队列优势在这里用不上 |
| LLM 调用 | LiteLLM / 直接 SDK / LangChain | **LiteLLM**。分层路由（DeepSeek 推理 / Qwen 出题）是成本策略基石，统一接口 + 故障转移支撑"LLM 降级成功率 ≥99%"硬指标。**弃用 LangChain**——对话控制走自研状态机，不需要其编排抽象 |
| 前端 | Next.js 14 App Router + TS | 服务端渲染 + 客户端交互平衡；App Router 的布局系统支撑"登录/应用双壳"；Next standalone 输出支持容器化部署 |

**面试可以这样讲**：每个选型都不是"别人用什么我用什么"，而是先立约束（单机内存、对话流式、领域无关），再对照候选逐项打分，砍不掉的组件才引入，砍掉的组件留好后置接口（repository 模式、embedding 预留字段）。

## 2. 系统架构

```
前端 Next.js（登录 | 对话 | 图谱 ReactFlow | 编辑器 | 市场 | 仪表盘）
        │ WebSocket / REST
API 层 FastAPI（JWT/邀请码认证 | 会话 | 诊断任务 | 报告）
        │
引擎层（领域无关核心）
  苏格拉底状态机(四态+自检)  诊断引擎(KST+BKT)
  图引擎(拓扑+权重路径/错题溯源)  遗忘调度(SM-2)
  评估层(引导纯度检测)  领域包加载器(schema 校验)
        │
数据层 PostgreSQL（用户/加密key | 会话/消息 | 掌握度 | 学习事件流 | 题库 | 图谱 JSONB）
        │
LLM 网关 LiteLLM → DeepSeek(推理) / Qwen(出题)，按用户 key 路由
```

**三条架构原则（面试重点）**：

1. **数据一致性是闭环的本质**。学生状态只有一份真相（PG）——诊断、辅导、复习读同一状态，各模块不各说各话。会话上下文快照存在 `sessions.context` JSONB，重启可从状态机快照恢复。
2. **引擎与内容彻底解耦**。领域包 = 5 个 JSON（manifest / knowledge_graph / questions / diagnostic_rules / assessment_config），引擎只认 schema 接口不认内容。接新学科 = 新增一个目录，零改引擎代码。
3. **可替换性后置**。图算法、任务队列、向量检索都压在接口后面：规模不到不引入，到了再换，换的时候只动 repository 层。

**关键澄清（避免面试答错）**：`purity_score`（引导纯度）是 messages 表的预留字段，API 层目前传 None，实时计算未接入——质量保障实际靠 OutputSanitizer + 提示词验收；复习调度运行时生效的是 **SM-2**（spaced_repetition.py），`scheduler.py` 的 [1,3,7,14,30] 档位设计存在但未被调用。

## 3. 核心功能实现（"怎么做的" + "为什么这么做"）

### 3.1 苏格拉底状态机：不直接给答案

**实现**：五态 `ELICIT → IDENTIFY → HINT → VERIFY → DONE`，10 个事件，一张 `TRANSITION_TABLE` 转移矩阵（states.py:41-72）定义唯一合法路径。`step()` 查表转移，维护 `consecutive_wrong` / `hint_level` 上下文。矩阵外组合直接抛错（如"未探明卡点不得给提示"）。

**为什么是状态机而不是自由对话**：LLM 自由发挥无法保证"不泄题"。状态机把教学法编码成硬约束——提示只能在 IDENTIFY 之后给，答案只能在 VERIFY 通过后确认。

**"不直接给答案"的六层机制**（这是本项目最能打的工程点）：
1. 转移矩阵硬约束（状态未到，行为不可能发生）
2. `OutputSanitizer` 规则自检：禁止最终答案句式 / 完整步骤 / 选项字母 / 数值泄露，命中重生成（最多 2 次），仍泄露降级为模糊话术
3. LLM 提示词显式禁令
4. mock 提示模板本身不泄露（无 key 时降级路径也安全）
5. 挫败感检测（连错 ≥3 降提示层级、≥4 切讲解）+ 拒答检测
6. 引导语质量评估 ≥90% 验收（scripts/eval_prompts.py 回归测试）

### 3.2 判题：规则层 + LLM 层双保险

- **选择题**：字母比对 + 选项内容匹配；多选集合全等
- **规则层**（judge_by_rule）：数字容差 <0.01 比较；关键词**双向包含**（标准答案在回答中 OR 回答是标准答案的语义子集）；长答案（>20 字）不武断判错，交 LLM
- **LLM 层**（judge_open）：语义等价判断优先，规则兜底；结果 `indeterminate` 时温和提示重答，**不推进状态机**（保证"不确定就不给结论"）

设计动机：规则层快、免费、确定性高，覆盖"x=2 与 2"这类确定场景；LLM 层处理语义等价（省略铺垫只答结论也算对）；两者互补，规则层兜底保证 LLM 抽风时不误判。

### 3.3 掌握度模型：BKT 概率 + SM-2 遗忘调度

- **BKT（贝叶斯知识追踪）**：参数 p_l0=0.3（初始掌握）、p_t=0.05（学习转移）、p_g=0.2（猜测）、p_s=0.1（失误），存领域包 diagnostic_rules.json（**每个领域可配**）。`bkt_update` 先应用学习概率 P(T) 再贝叶斯后验，按 student+pack+node upsert 到 `mastery_states`。
- **遗忘调度用 SM-2**：ease 1.3-2.8、答错衰减 0.2 / 答对增益 0.1，间隔 0→1→3→3·ease^(n-1)，落 `review_schedule` 表；到期题在会话开始时注入，优先出题。
- **事件流**：`learning_events` 表记录每个作答事件（event_type/node_id/payload JSONB）——评估的唯一依据，掌握度可重算可审计。

### 3.4 诊断引擎：KST 加权轮盘赌选题

`select_next_question`：priority = `weakness×10 − |difficulty−0.6| − recency×2.5`，然后**加权轮盘赌**（不是必选最高分，而是概率选——避免总是同一道题，保留探索性）。终止条件：根因置信度（1−min(mastery)）≥0.8 或 15 题上限。

**边界**：diagnostic_rules.json 里声明的 `initial_strategy`（weakest_node / importance_first）实际只实现了 weakest_node 行为——面试中主动说明"这是声明了两种策略但只落地一种"，比被问穿强。

### 3.5 图引擎：拓扑 + 权重路径规划 / 错题溯源

- 内存邻接表（prereq/succ），Kahn 拓扑排序（**有环抛错**——建图校验层同步保证无环）
- `plan_path`：薄弱节点 ∪ 全部前置祖先，按（拓扑序, -importance, difficulty）取前 10 生成个性化路径
- `trace_root`：沿祖先链取掌握度最低节点；`trace_root_evidenced`（M3 精细化）**只用已作答过的祖先**判根因——修复了"未测节点默认 P(L0) 相同导致随机选根因"的缺陷

### 3.6 LLM 网关：分层路由 + 三级降级 + 用户 key 加密

- `generate(role, prompt, ctx)` 统一入口；无 key → 确定性 mock（开发/演示零成本可用）
- **分层路由**：diagnostic/tutor → DeepSeek-v3（推理主力）、generate → Qwen-turbo（出题便宜）；用户可在设置里自选模型（qwen-turbo/plus/max/long + deepseek-v3/r1）
- **三级降级**：L1 备用模型 → L2 模板话术 → L3 离线提示，支撑"LLM 降级成功率 ≥99%"
- **用户 API key**：`user_api_keys` 表，**Fernet 对称加密**（API_KEY_ENC_KEY），展示仅掩码 sk-****abcd；每请求按当前用户路由——用户 key 优先，系统级 key 仅开发/内部用途，不做用户兜底

### 3.7 领域包体系：内容即配置

- 5 个必选文件（PACK_FILES）：manifest / knowledge_graph / questions / diagnostic_rules / assessment_config
- `load_pack` 逐文件 pydantic 校验，**fast fail**，manifest.id 必须与目录名一致
- 保存额外业务校验：节点 id 唯一、step_node_map 指向存在节点、选项 ≥2、prerequisite 边**无环（DFS 三色标记）**
- 默认包生成器 pack_factory 可一键生成合法空包（用于编辑器起步）

### 3.8 图谱编辑器（React Flow）

- 三明治布局：工具栏 / ReactFlow 画布（自定义节点，难度权重徽标）/ 右侧 380px 属性面板
- **撤销/重做**：`(pack, nodes, edges)` 三元组快照 + past/future 双栈，上限 50 步；`structuredClone` + `JSON.stringify` 去重防表单 onBlur 连发；Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y 快捷键，**输入框内不拦截**（保留浏览器原生文本撤销）
- **连边**：防自环、防重复边；删节点同步清理 edges 和题目 step_node_map
- 只读模式：非本人包 `editable=false`，拖拽/连边/删除全禁用（"我的领域"里看别人的包只读）
- 导入 JSON = 整包替换**仅内存**（"请核对后点保存写入"），导出 = Blob 下载——**内存暂存 + 显式保存**的设计避免误操作直接毁包

### 3.9 领域市场 + 审核流

- 发布：private 直接 published；public → **pending_review** 等管理员审核
- 管理员：`user.meta.is_admin` 标记（make_admin.sh 用 psql jsonb_set 设）
- 审核 API：`GET /admin/domains?status=pending_review`（限 50，非管理员 403）→ approve / reject+reason
- 市场只展示 `public AND published`；举报即置 takedown（简化但够用）

### 3.10 邀请码注册

- 首用户免邀请码（users 表空时跳过），第二个用户起必填——**保证线上不是开放注册**，控制体验者质量
- 每人最多 5 个未使用邀请码（MAX_ACTIVE）、7 天有效、一次性消费（used_at）
- 前端 `/auth/bootstrap` 返回 needs_invite 动态显隐邀请码输入框
- 运营侧 make_invites.sh 批量生成（GUEST01..20 多值 INSERT + ON CONFLICT）

### 3.11 主题系统：CSS 变量双通道

- 5 套 accent（墨蓝/星夜紫/森绿/海洋蓝/落日橙）× auto/light/dark
- `applyTheme` 操作 `document.documentElement.dataset.mode/accent`；dark 双通道：系统偏好自动暗色 + 手动暗色覆盖
- `useThemeVar` 用 getComputedStyle 读 CSS 变量 + 监听 `at-theme-change` 事件——**Canvas/图表/编辑器也能取到主题色**（纯 CSS 变量方案解决"canvas 里取不到 CSS 变量"的常见坑）
- 偏好存 localStorage（at_mode/at_accent）

### 3.12 部署体系：2C4G 单机 Docker Compose

- 5 服务：postgres（pg16 + pg_isready healthcheck）/ api（8010 + /healthz healthcheck）/ web（3000，NEXT_PUBLIC_API_BASE 构建时注入）/ portainer（容器管理面板）/ uptime-kuma（可用性监控）
- **backend/Dockerfile**：python:3.12-slim，内置包复制为只读基线 `/app/domain_packs_builtin`；**entrypoint 首次同步到持久卷（! -d 才 cp，不覆盖用户自建包）→ alembic upgrade → 幂等 create_all + 补列兜底**
- **frontend/Dockerfile**：三阶段，Next **standalone** 自包含输出 + 非 root 用户
- deploy.sh 六步一键：装 Docker → 生成密钥 → 自动取公网 IP → 写 NEXT_PUBLIC_API_BASE 与 CORS → build up → 轮询 healthz → 打印访问地址
- 密钥：API_KEY_ENC_KEY（Fernet 32 字节 urlsafe base64）+ JWT_SECRET（64 hex），.env.production 不入库（.gitignore 防护）

## 4. 真实遇到的难点与解决（面试讲"故事"的部分）

### 4.1 线上登录全部失败：NEXT_PUBLIC_API_BASE 构建时注入的坑
**现象**：部署后浏览器登录报"网络连接失败，请检查后端服务是否在运行"，但服务器上 curl 后端 healthz 正常。
**排查**：抓线上 login chunk JS，发现内联的 API 地址是 `http://localhost:8010`——浏览器访问线上页面时，请求发到了**访问者自己电脑**的 localhost。
**根因**：`NEXT_PUBLIC_*` 是 Next.js **构建时**内联变量。手动 `docker compose build web` 时没传该 env，用了 compose 默认值 `http://localhost:8010`；容器重启不触发重新构建，所以光重启没用。
**解决**：把 `NEXT_PUBLIC_API_BASE=http://<IP>:8010` 写入仓库根 `.env`（compose 自动读取做变量替换，持久化），重建 web 镜像。
**教训**：区分"运行时 env"和"构建时 env"；NEXT_PUBLIC_* 出问题必须重建镜像而非重启容器；用浏览器抓 chunk 而不是只看服务器日志。

### 4.2 欢迎页动效卡顿：三个隐性性能源
**现象**：品牌名解密 + 副标题轮换 + 按钮浮现"明显卡顿"。
**逐层排查**（每层都有实测证据）：
1. ClickSpark 组件的 rAF 循环**常驻运行**——无火花也每帧 clearRect + 请求下一帧，60fps 持续占主线程，跟文字动画抢帧 → 改为按需启停（空闲时循环完全停止，实测 canvas toDataURL 两次采样一致）
2. 副标题挂着 CSS 动画 `welcome-fade`（opacity+transform 0.9s），与 motion 字符动画**双重竞争同一属性** → 移除 CSS 动画，统一交给 motion 驱动
3. 解密组件 setInterval 每 tick 触发 2 次 React 重渲染 → 降低 tick 频率
**教训**：动效卡顿先查"常驻循环/动画竞争"，用 canvas toDataURL 采样、getComputedStyle 等**可量化的证据**定位，而不是靠感觉。

### 4.3 组件库适配踩坑：BlobCursor 布局破坏
**现象**：引入鼠标跟随墨点特效后，欢迎页文字不再居中、墨点不可见。
**根因**：组件容器是 `relative w-full h-full`，而父级是 `min-h-screen`（无固定高度）→ `h-full` 解析为 0 → 墨点被 overflow-hidden 裁剪；且容器在 flex 布局里占位，把 justify-center 撑偏。
**解决**：容器改 `fixed inset-0`（脱离文档流 + 全视口）；后续再引入这类"覆盖层"组件（ClickSpark）时直接预判：覆盖层必须 fixed 定位，不参与父级布局。
**教训**：从第三方组件库引入组件，第一件事是看它的**容器定位方式**是否会破坏宿主布局；trailCount 与 sizes 数组必须等长（数组越界产生 NaN 渲染）。

### 4.4 后端 reload 失效：路由 405
**现象**：改了后端路由，前端请求一直 405；`--reload` 看似在跑但没生效。
**排查**：确认 watchfiles 在 Windows 上监控失效 → 杀掉旧 uvicorn 进程重启。
**教训**：开发期依赖 reload 前先验证它真的 reload 了；部署环境（容器内）用健康检查轮询而非依赖 reload。

### 4.5 困难档题目不足："纯困难"诊断出不满 15 题
**现象**：用户选"困难 + 15 题"，实际只出了 1 道题——hard 档（≥0.66）题库只有 1 道。
**分析**：先做难度分布统计（各档位题量），确认 0.65 档有 4 道可上调、0.6 档有 60 道可精选，0.75 是合法上限。
**解决**：写脚本批量上调难度（只改 difficulty 字段，题干/答案不动），hard 档从 1 道补到 15 道左右。
**教训**：内容质量问题（题量分布）用**数据统计**说话，先量化再动手；改数据用脚本 + dry-run 先看改动清单。

### 4.6 部署环境连环坑（镜像构建期）
- **python-multipart 缺失**：FastAPI 表单接口启动即崩 → 补依赖（这种错在本地 dev 不出现，因为本地环境早就装过——容器是干净环境，必须以 requirements 为准）
- **useSearchParams 需 Suspense**：Next 生产构建 prerender 强制要求 → 页面包 Suspense 边界
- **Next standalone**：默认输出不自包含，容器里起不来 → next.config 开 `output: "standalone"`
- **端口被 WSL 转发占用**：本地 8010 被 wslrelay 占用，误以为后端没起
- **服务器内存不足**：2C4G 上 build 前端镜像偶发 OOM → 本地 build 好镜像再传，或加 swap

### 4.7 掌握度面板"只剩一根竖线"
**现象**：仪表盘"整体掌握度"环形图只剩一条竖线。
**根因**：环形图依赖 mastery_states 数据，测试账号没有掌握度记录时环形退化。**造数据验证**（插入两条 mastery 记录）确认是数据问题而非渲染问题。
**教训**：图表类 bug 先确认"是数据没有还是渲染坏了"——造最小数据即可区分，避免在渲染层瞎调。

## 5. 临场处理框架（面试时怎么讲）

我在这个项目里形成了固定的排障闭环，面试时可以套用：

```
现象（可复现） → 定位（抓 chunk / 看日志 / 数据统计 / 最小复现） → 根因（不是症状） → 修复（最小改动） → 验证（可量化证据） → 防复发（持久化 / 脚本 / 文档）
```

举例：线上登录失败 → 抓 JS chunk 看到 localhost → 根因是构建时 env → 修复后**抓新 chunk 验证**内联地址变了 → 把地址持久化到 .env 防复发。每一步都有"证据"而不是"我觉得"。

**讲项目时主动暴露边界**（加分项）：
- "purity_score 字段预留了但实时计算没接，质量靠 sanitizer + 验收测试"
- "initial_strategy 声明了两种策略只实现了 weakest_node"
- "GLM 只在枚举里，没实际接模型"
- "scheduler 档位设计没启用，运行时是 SM-2"
主动说边界，说明你清楚自己系统的真实状态，比被追问穿帮强。

## 6. 面试追问预案（Q&A）

**Q1：为什么不用 Neo4j？**
规模是"单章节 30-50 节点"，依赖查询是浅层遍历，PG JSONB 完全够；Neo4j 在 16GB 机器上要吃掉 3-5GB 常驻内存，代价远超收益。等扩展到万级节点再评估，接口层已按可替换设计。

**Q2：LLM 判题会不会误判？**
双层设计：规则层（数字容差、双向包含）覆盖确定性场景且免费；LLM 处理语义等价；`indeterminate` 结果不推进状态机而是温和重答。规则层是兜底，LLM 抽风不会直接误判。

**Q3：怎么保证不直接给答案？**
六层机制，最硬的是状态机转移矩阵（行为被状态约束）和 OutputSanitizer 规则自检（输出被规则约束）——不是靠提示词"求求你别泄题"，而是结构上做不到。

**Q4：掌握度怎么算的？**
两层：BKT 贝叶斯后验更新 P(掌握)（参数每领域可配），SM-2 管复习时间窗（ease 自适应）。学习事件全量落库，掌握度可重算。

**Q5：前端为什么用 Next.js 而不是 Vite SPA？**
App Router 布局系统支撑登录/应用双壳，SSR 有利于首屏与分享；最重要的：`output: standalone` 让容器化部署极其干净（一个 node server.js 就跑起来）。

**Q6：如果用户量上来了怎么办？**
分层的答案：任务队列换 Celery（接口已预留）、向量检索换 pgvector（字段已预留）、图数据库看规模、Redis 加缓存层。**所有"未来要换的"都在架构里留了接口**——这是当初选型的准则。

**Q7：这个项目你遇到最难的问题是什么？**
线上登录全挂那个最"痛"（环境问题隐蔽、排查链路长），欢迎页卡顿那个最"技术"（三个隐性性能源叠加）。两个都能完整讲出"现象→定位→根因→修复→验证"闭环。

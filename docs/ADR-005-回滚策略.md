# ADR-005：回滚与数据恢复策略（每日备份 + Alembic 迁移 + 状态机回滚）

> 状态：**已接受（2026-08）** · 关联：docs/02 §3.2、docs/04 决策、`scripts/backup.py`

## 背景

系统是"长期真实可用"定位（README 定位声明），数据不能丢、出问题可修。需要覆盖三种回滚场景：**代码回滚、数据恢复、对话状态回滚**。

## 决策

三层回滚策略：

1. **代码/引擎回滚**：状态机设计保证**确定性**——每轮对话的状态转移可追溯（trace_id），出问题可定位到具体转移；代码回滚走 git（主分支提交粒度为功能单元，可 revert 到任一里程碑）
2. **数据恢复**：`scripts/backup.py` 每日 `pg_dump` → gzip → `D:\AdaptTutorBackup`，保留最近 N 份（默认 7），支持 `--dry-run` 预演；恢复用 `pg_restore`/psql
3. **会话状态回滚**：`sessions.context` JSONB 存状态机快照（状态 + 掌握度 + 路径），**M3 验证会话恢复 100%**——对话中断/异常可恢复续聊，不会状态错乱

## 为什么

1. **数据是核心资产**：学习数据（mastery/events/会话）不可再生，备份是底线（02 §3.2"每日备份成功；每阶段 ≥1 次恢复演练"）
2. **状态机确定性 → 回滚成本低**：不用"猜"状态怎么来的，trace_id 可回溯
3. **快照恢复 vs 重算**：存快照比从事件流重放简单可靠（M3 实测恢复 100%）

## 后果

- 正面：数据可恢复、会话可续、代码可回滚，符合"长期可用"
- 代价：备份需磁盘空间（保留 7 份 gzip）；恢复演练是运维纪律需定期执行（架构检查单"M4r18 验证恢复路径存在"）
- 演进：上云后补云备份（04 上云前置项），本地策略作为基线

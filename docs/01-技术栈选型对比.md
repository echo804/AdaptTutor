# 01-技术栈选型对比

> 每项选型给出候选对比、结论与弃用理由。**决策准则**：单机 16GB 内存约束优先；复杂度换必要性；能砍则砍，接口后置。

**版本约定（与 00-环境搭建.md 一致）**：Python 3.12（`py -3.12`）、Node 20 LTS、PostgreSQL 16+、Docker Desktop（WSL2 后端）。

---

## 1. 后端框架：FastAPI vs Flask vs Django

| 维度 | FastAPI | Flask | Django |
|---|---|---|---|
| 异步 | 原生 async/await + WebSocket | 需插件（flask-sock），生态弱 | 3.x 起支持 async，重 |
| 数据校验 | Pydantic 原生 | 需 marshmallow | DRF 序列化 |
| WebSocket | 原生支持（本项目对话实时流式） | 弱 | 需 Channels，重 |
| 重量 | 轻 | 最轻 | 重（ORM/Admin/Auth 全家桶） |
| 生态 | AI 项目事实标准 | 传统 | 传统 CMS/后台 |

**结论：FastAPI**。WebSocket 原生支持是刚需（对话流式），异步 IO 契合 LLM 调用场景，Pydantic 同时服务数据校验与领域包 schema 校验。Django 全家桶在单机项目里是负担。

---

## 2. 图谱存储：PostgreSQL JSONB vs Neo4j vs pgvector

| 维度 | PG JSONB + 应用层图算法 | Neo4j | pgvector（仅向量） |
|---|---|---|---|
| 内存占用 | 共享 PG 进程（1.5GB 总预算内） | **JVM 常驻 3-5GB 独立进程** | 共享 PG |
| 图查询 | 应用层遍历（拓扑/依赖链，章节级 ≤500 节点） | Cypher 原生 | 不支持图 |
| 数据一致性 | 图谱与业务数据同一事务 | 需跨库同步 | 需跨表 |
| 复杂度 | 无新组件 | 新组件 + 运维（备份/升级） | 低但解决不了图问题 |
| 规模上限 | 万级节点可跑（本项目 ≤500） | 十万级以上强 | — |

**结论：PostgreSQL JSONB + 应用层图算法**。本项目图谱规模为"单章节 30-50 节点"，依赖查询（前置链、溯源路径）是浅层遍历，PG 内做完全够。Neo4j 的唯一优势（原生图查询）在 ≤500 节点的规模上不成立，代价却是 16GB 机器上最贵的 3-5GB 内存与一套独立运维。**弃用 Neo4j**。

**后置条件**：若未来领域包扩展到全学科（万级节点 + 复杂多跳查询），再评估引入图数据库；接口层（图谱加载/查询）设计为可替换（repository 模式）。

## 3. 题目检索：标签过滤 vs Qdrant vs pgvector

| 维度 | 标签过滤（SQL） | Qdrant | pgvector |
|---|---|---|---|
| 内存 | 0（PG 内） | ~0.5GB 独立进程 | 共享 PG |
| 适用规模 | 千级题库足够 | 十万级+ | 万级+ |
| 语义检索 | 无（靠人工标签） | 有 | 有 |
| 复杂度 | 0 | 新组件 | 需 embedding 计算 |

**结论：标签过滤**。领域包 1 题库仅 100+ 题，按"知识点标签 + 难度 + 错误模式"组合过滤即可覆盖全部检索需求（同知识点变式题、难度匹配）。**Qdrant 弃用**；question_bank 表预留 `embedding` 字段，题目规模 > 5000 或出现语义检索需求时引入 pgvector（同库、零新进程），Qdrant 不再考虑。

---

## 4. 任务队列：FastAPI 后台任务 vs Celery + Redis

| 维度 | FastAPI BackgroundTasks | Celery + Redis |
|---|---|---|
| 内存 | 0 | Redis ~0.2GB + worker ~0.3GB |
| 可靠性 | 进程内，重启丢失 | 持久队列 |
| 适用 | 短任务（诊断计算、报告生成 ≤ 分钟级） | 长任务/分布式 |
| 复杂度 | 0 | broker + worker + beat + 结果后端 |

**结论：FastAPI 后台任务**。本项目"耗时任务"仅有诊断计算与报告生成，均为分钟级、无跨进程诉求；任务状态持久化在 PG（sessions.status），重启后可从 PG 恢复会话。**Celery + Redis 弃用**。

**后置条件**：后台任务开始阻塞 API 请求或需要多 worker 时，引入 Redis + 简单队列（接口预留：任务提交/查询走统一抽象）。

---

## 5. LLM 调用：LiteLLM vs 直接 SDK vs LangChain

| 维度 | LiteLLM | 直接 SDK（openai/deepseek/qwen 各自） | LangChain |
|---|---|---|---|
| 多模型统一 | ✅ 统一接口 + 自动切换/故障转移 | ❌ 每家一套 SDK | ✅ 但抽象重 |
| 成本 | 低（一个网关层） | 低 | 高（学习/调试成本） |
| prefix caching | ✅ 支持 | 各家自己调 | 需插件 |
| 锁定风险 | 低（OpenAI 兼容协议） | 高 | 中 |

**结论：LiteLLM**。分层路由（DeepSeek 核心推理 / Qwen 出题 / GLM 工具）是项目成本策略的基石，LiteLLM 的故障转移与统一接口直接支撑"LLM 降级成功率 ≥ 99%"硬指标。直接 SDK 需自研多供应商路由，成本高于 LiteLLM 本身。**LangChain 弃用**——本项目对话控制走自研状态机（见第 6 项），不需要其编排抽象。

**按用户 key 路由**（对齐 04 2.9）：用户自配 key（`user_api_keys` 表，Fernet 加密），`llm_gateway` 每请求按当前用户传 key——优先用户级，系统级 `LITELLM_API_KEYS` 仅开发/测试/内部用途，不作为用户兜底。

## 6. 对话控制：自研四态状态机 vs LangGraph

| 维度 | 自研状态机（FA） | LangGraph |
|---|---|---|
| 控制粒度 | 完全确定：四态流转 + 非法跳转拒绝 | 图编排，灵活但约束弱 |
| 可测试性 | 状态转移矩阵可单测全覆盖 | 依赖图执行测试 |
| 内存/依赖 | 0（纯代码） | 依赖库 + 抽象层 |
| 适配本项目 | 苏格拉底对话就是有限状态机（探明→诊断→提示→验证） | 用其表达状态机是杀鸡用牛刀 |

**结论：自研四态状态机**。本项目核心铁律"不直接给答案"需要**确定性约束**——状态机硬约束 + 输出自检层，这正是 LLM 非确定性的克星；LangGraph 的灵活性在此是反需求。自研状态机可测试、可回滚（状态可持久化到 PG 恢复）。**LangGraph 弃用（保留可选项标记，不引入）**。

---

## 7. 前端：Next.js vs 纯 React + Vite

| 维度 | Next.js 14 | Vite + React |
|---|---|---|
| SSR/SEO | ✅ | ❌（纯 CSR） |
| 生态 | React Flow、KaTeX 均兼容 | 同 |
| 复杂度 | 路由/构建约定多 | 更简单 |
| 本项目需要 | 无需 SEO；单页应用 + WebSocket | 完全够用 |

**结论：Next.js 14（保留，但用极简模式）**。规划书 V1.0 已选 Next.js，生态与 React Flow 兼容性已验证；本项目虽是单页应用，但 Next.js 的开发体验与未来可能的服务端渲染需求值得保留。**不引入新的 SSR 框架，不引入 UI 组件库**（TailwindCSS 手写即可），避免前端复杂度膨胀。白板/多模态前端功能明确不做。

---

## 8. 可观测性：结构化日志 + trace_id vs OpenTelemetry + LangFuse

| 维度 | 结构化日志（JSON + trace_id） | OTel + LangFuse |
|---|---|---|
| 内存 | 0 | 各 ~0.2-0.5GB collector + 存储 |
| 追踪 | trace_id 贯穿消息/事件/评估记录，可 SQL 查询回溯 | 分布式追踪 UI |
| 复杂度 | 低（logging + 中间件） | 高（exporter/collector/存储） |
| 单机适用 | ✅ | ❌ 过重 |

**结论：结构化日志 + trace_id（JSON 落盘 + PG 事件表）**。硬指标"100% 会话可凭 trace_id 回溯"用结构化日志 + learning_events 表即可达成；LangFuse 的评估可视化在单机场景是负担。**OTel/LangFuse 后置**：若未来需要跨服务追踪或可视化评估面板，再引入（评估数据已在 PG，可平滑导出）。

## 9. 选型汇总与版本基线

| 层 | 选型 | 版本/形态 | 弃用（V1.0） |
|---|---|---|---|
| 后端框架 | FastAPI | Python 3.12 | — |
| 认证 | 自研 JWT + bcrypt（FastAPI 生态） | 邀请码注册；弃 Keycloak/Auth0 | Keycloak/Auth0 |
| 图谱存储 | PostgreSQL JSONB + 应用层图算法 | PG 16+ | Neo4j |
| 题目检索 | 标签过滤（SQL） | 预留 embedding 字段 | Qdrant |
| 任务队列 | FastAPI BackgroundTasks | 任务状态持久化 PG | Celery + Redis |
| LLM 网关 | LiteLLM | 多供应商路由 + 按用户 key | 直接 SDK |
| 对话控制 | 自研四态状态机 | 状态持久化可恢复 | LangGraph |
| 前端 | Next.js 14 + @xyflow/react + TailwindCSS + KaTeX | Node 20 LTS | 白板 |
| 可观测性 | 结构化日志 + trace_id | JSON 落盘 + PG 事件表 | OTel + LangFuse |
| 部署 | Docker Compose | 三服务（postgres/api/web；local/prod 两套 compose） | — |

**依赖清单（后续写 pyproject.toml 依据）**：fastapi、uvicorn[standard]、sqlalchemy[asyncio]、asyncpg、alembic、pydantic、pydantic-settings、litellm、bcrypt、PyJWT、cryptography（Fernet）、pytest、httpx。前端：next@14、@xyflow/react、katex、tailwindcss。

## 10. 选型变更纪律

- 任何选型变更须写 ADR（决策记录），说明：问题、候选、结论、代价、后置条件。
- 后置项（pgvector/Redis/OTel）在触发条件满足前**不允许提前引入**——这是 16GB 内存与单人维护的根本保障。

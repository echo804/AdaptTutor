### 0.2 零成本红线（不是任务，是"别踩"，不占工期）

1. **不要执行 `backend/scripts/cleanup_test_data.py`**（P5-1/P5-2）。它按不受限的用户名前缀 `u_` 判定"测试账号"并硬删用户+全部学习数据，**且默认（不加 `--dry-run`）就真删**。当前它因删除顺序违反外键而必然回滚，恰好掩盖了风险——所以只要不执行就安全。
2. **如果要公网部署**，先换掉 `.env` 里的占位符 `JWT_SECRET`（P0-1）。本地开发无所谓；公网实例上任何人可用它自签 token 冒充任意账号（含管理员，已实测）。

### 0.3 核心功能优先的"最该先动的四件事"

1. **辅导页卡片 → 对话流**（第 7 章）：答错即死锁（用户反馈 #4）、引导语一个字不显示、本轮完成语被吞——这三个是同一个范式错误，一次改完。
2. **判题规则层会误判**：残缺答案判对、数字对调判对；而 `judge_open` 一旦规则判对就跳过 LLM，误判**无法被纠正**。影响面实测：144 道填空/解答里 119 道（83%）的答案是文本型。
3. **变式题在数学上不自洽**（选项平移后选项里没有正确答案），而它正是 VERIFY（变式验证）环节的题目来源。
4. **防泄题自检层只覆盖 1 条路径**：`OutputSanitizer` 全仓只在 `_hint_turn` 被调用一次，💡 求助接口（最可能泄露答案的入口）完全不过自检——而"不直接给答案"是产品第一承诺。

### 7.0 前置判断的更正：这**不需要**先改后端

> 术语：下文的 **A 刀 = 第一步，只改前端**（1 个文件）；**B 刀 = 第二步，改后端契约**（3 个文件）。两者互相独立，可分开做、分开验证。

我此前把这项排到"第 5 批（需先定契约）"，理由写的是"契约不改，前端做不对"。**复核后这个理由不成立。**

**为什么只改前端就能做对**：做"对话流"需要的三样东西，后端**本来就在给**，只是现在的界面没用或没用对：

| 需要什么 | 后端现在有没有 | 现状（问题所在） |
|---|---|---|
| 当前处在哪个状态（探明/识别/提示/变式/结束） | ✅ 每次响应都返回 `state` | 现在只用来点亮顶部四个小圆点，**没参与任何判断** |
| 老师说的引导语 | ✅ 每次响应都返回 `message` | **界面一个字都不渲染** → 这就是"答错后什么都做不了"的根因之一（P1-2） |
| 历史对话全文 | ✅ 接口 `GET /sessions/{id}/messages` 存在 | **前端从来没调用过**（全仓 grep 0 处）——接上它就有了"思路轨迹回看" |

而当前的死锁来自这条**猜出来的**规则：

| | 旧规则（错） | 新规则（够用） |
|---|---|---|
| 依据 | `judged = r.correct !== null`（`:283`） | `r.state` |
| 问题 | `correct=False` 在后端有**三种**含义（真答错 / 诊断不支持追问 / VERIFY 非答案输入，见 P2-2），一律被当成"判分结束"→ 关掉作答区 | `closed = r.state === "done" \|\| 推送了新题` —— 与 `correct` 的语义完全无关 |

**结论**：A 刀（前端单文件）可独立完成并验证；契约清理（P2-1/2/3）依然要做，但它是"让规则更干净"，不是前置条件。我此前把它当成前置条件，是错的。

### 7.4 唯一判定规则（实现时以此为准）

```ts
// send() 拿到响应后
const judged   = r.correct !== null;                      // 只决定"要不要显示判词"
const newQ     = r.question;
const sameQ    = !!newQ && !!question && newQ.id === question.id;
const pushed   = !!newQ && !sameQ;                        // 换题 → 上一题终结
const finished = r.state === "done" || r.done === true;

setQuestion(newQ ?? (finished ? null : question));
setClosed(finished || pushed || !newQ);                   // ← 死锁在这里被消除
```

**关键点：`closed` 只由 `state` 与"是否换题"决定，与 `correct` 无关。** 这样 P2-2 的三条路径（变式答错 / 变式阶段追问 / 本轮完成）都不会再锁死输入。

### 7.5 界面结构（对齐原型）

```
┌ 会话头：退出 · 领域名 · 台阶刻度（探明 / 识别 / 提示 / 变式）────────────┐
├──────────────────────────────────┬──────────────────────────────┤
│ 对话流（可滚动，自动到最新）        │ 当前题卡（常驻参照）           │
│  · AI 消息（追问时：强调色 + 左细竖线）│ · 第 N / M 题                 │
│  · 学生消息（右侧块，文字左对齐）     │ · 题干 + 选项（已选标注）      │
│  · 判词（克制，仅状态不作装饰）       │ · 当前知识节点 + 掌握度        │
│  · 思路轨迹（仅学生自己的表述，折叠）  │ · 答案闸门（未解锁 / 解锁）    │
├──────────────────────────────────┴──────────────────────────────┤
│ 作答区（常驻底部）：[先打草稿] ⇄ [想清楚了，转成作答]      [提交]     │
└─────────────────────────────────────────────────────────────────┘
```

- 题卡**不进对话流、不吸顶**（已裁决：一个元素不能同时是"消息"和"面板"）。
- 台阶刻度用**横刻度**，竖线留给"追问"（05 §5.1 规定竖线是该语义的专属符号）。
- 强调色只出现在三处：当前追问 / 当前知识节点 / 可点元素。
